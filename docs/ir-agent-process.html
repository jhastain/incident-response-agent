End-to-End Process

Alert to Resolution

From the moment an alert fires to knowledge base storage — every step is automated, auditable, and designed for speed of insight over speed of execution.

1
T+0s

Alert Classification

LLM classifies the incoming alert into 1 of 11 categories (application-errors, sql-database, cloud-infrastructure, performance, deploy-release, auth-security, scheduled-jobs, data-integrity, business-logic, monitoring-meta, pubsub-messaging) and assigns severity (sev1-sev4), service name, GCP project, and environment. Output: structured AlertClassification (Pydantic schema) stored as {classification}.

11 Categories Pydantic Schema output_key: classification
2
T+3s

Context Loading (Parallel)

ParallelAgent loads two context sources simultaneously:
• historical_context — Queries Firestore for similar past incidents (find_similar_incidents) and learned triage steps (get_triage_guidance), with GCS fallback for older incidents.
• infra_context — Loads service metadata, GCP project mappings, and dependency information from the GCS context/ prefix.

Hypothesis-Driven Synthesis

Merges findings from all Tier 1 agents. Forms top 3 hypotheses ranked by evidence strength. For each hypothesis: cites supporting evidence, refuting evidence, and what remains unknown. Dispatches Tier 2 agents to TEST the leading hypothesis — not just category-based routing.

Conditional agents dispatched based on hypothesis testing needs and category. Each agent tests a specific aspect of the leading hypothesis. Time budget: 2 minutes per agent.

Report Generation

Structured Teams-ready report with 6 sections: Executive Summary, Top Hypotheses (ranked by evidence), Suggested Mitigations (drain/rollback/restart/scale/isolate/escalate), Evidence Details, Investigation Timeline, and Next Steps. Confidence levels: STRONG / MODERATE / WEAK / UNKNOWN — never "CONFIRMED".

T+5.5min

Verification

Independent quality check using Gemini 2.5 Flash. Scores diagnosis confidence, solution actionability, and investigation efficiency. Automated tier: MEDIUM/LOW/UNRELIABLE (never HIGH without human validation). Flags low-confidence findings before they reach production use.

Persistence

Dual-write to GCS and Firestore. Stores complete incident JSON with verification scores, investigation timeline, and all agent findings. GCS: gs://incident-summaries/ for archival. Firestore: incidents collection for fast queries and historical similarity search.

Safety Architecture

Five-Layer Defense Model

Adapted from Google's SRE safety architecture. Each layer independently prevents a class of failure. All five must be breached for an unsafe action to occur.

1

Deterministic Tools

Strictly typed MCP tools via Bifrost. Per-server read-only allowlists (Datadog: 5 tools, ADO: 5, Sentry: 4). No arbitrary commands.

2

Token + Time Budgets

Per-agent token limits and time budgets. Agents that exceed 80% must checkpoint. At 100%, force-stop with partial findings.

3

Investigation Rules

20 non-negotiable rules baked into every agent prompt. Including: facts before hypotheses, test hypotheses don't collect data, suggest mitigation don't just diagnose.

4

Human-in-the-Loop

Phase 1: L1 Assisted Autonomy. All findings posted to Teams for human review. No automated actions. Engineers direct the investigation.

5

Global Emergency Stop

Red Button: /pause endpoint halts all in-flight agents, queues new webhooks. Firestore flag checked before every tool call. Full audit trail.

Progression Gates

L1 → L2: 50+ incidents processed, <5% false positive rate
L2 → L3: Suggestion accuracy >80% on 100+ incidents
L3 → L4: Mitigation success >95% with safety controls

Dynamic Downgrade

Auto-downgrade to lower autonomy when:
  • Peak traffic detected
  • Multiple active incidents (storm)
  • Agent confidence below threshold
  • Red Button activated
Architecture

Platform Components

Cloud Run hosted, ADK orchestrated, Bifrost routed. Designed for isolation (one container per incident) and resilience (checkpoint + resume on restart).

Ingestion

Alert Input

Alerts submitted via ADK web UI or Agent Engine API. Webhook frontend (FastAPI on Cloud Run) is planned for Phase 2.

Orchestration

ADK 2.2.0 Orchestrator

LlmAgent via Vertex AI Agent Engine. 8-stage pipeline: classifier → context_parallel → tier1_parallel (9 agents) → synthesis → tier2_dispatcher → report → verification → persistence. Model: claude-sonnet-4-6 via LiteLlm.

LLM Routing

Bifrost Gateway

Semantic cache. Virtual keys + budget. MCP server aggregation. Per-server read-only tool allowlists. Shared singleton McpToolset with response truncation (4000 char limit).

Data Layer

Firestore Collections

Native mode, us-central1, aiops-dev-project. Collections: incidents, decision_trees. Compound queries for structured search. Transactions for dedup and state.

Interface

Teams Bot

Planned for Phase 2. Currently, reports are generated but not auto-posted to Teams.

Messaging

Pub/Sub

Planned for Phase 2. Pub/Sub topic will decouple webhook frontend from investigation lifecycle.

Informed By

Google SRE AI Principles Adopted

Key principles from Google's SRE AI engineering practices that shaped this platform's design.

1

Mitigation-First

Every finding includes a suggested Generic Mitigation (drain, rollback, restart, scale, isolate, escalate). Diagnose AND prescribe.

2

Bounded Action Space

Agents follow numbered checklists with typed MCP tools. No open-ended exploration. Each step tests a specific hypothesis.

3

Progressive Trust

L1 → L2 → L3 → L4 autonomy levels. Each gate requires demonstrated reliability on evaluation data. Dynamic downgrade on elevated risk.

4

Insight Speed > Execution Speed

Surface the most important signal first. Don't wait for all agents. Incremental findings posted to Teams as they arrive (Rule 8).

5

Virtuous Loop

Every resolved incident feeds the knowledge base. Embedded golden data collection: responders rate each finding's accuracy. Postmortems become training data.

6

Chain-of-Thought Transparency

Full audit trail: every tool call, hypothesis considered, evidence for/against, confidence rationale. Stored in Firestore incident records for debugging and evaluation.
