How the agent decides where to dig

Every alert
routes itself through
a decision tree.

The agent doesn't run everything every time. It classifies the alert into one of 11 categories, then a per-category decision tree decides which specialists to wake and in what order — so a SQL deadlock and a Pub/Sub backlog get different teams.

01 / THE MODEL

Two decisions drive the whole run

Classification picks the lane. Routing picks the team. Everything downstream follows from these two.

Input

Free-text from PagerDuty, Datadog, GCP, Sentry or Teams.

03 / THE TREE

Inside one tree — and how it sharpens

Each category carries an ordered triage playbook: which agent to ask first, second, third. Here's sql-database. The order is meant to put the highest-yield check up front.

sql-database · triage order
1datadog_observability — DB perf metrics & slow queriesT1
2sql_dba — analyze query perf & blockingT2
3gcp_logging — search for DB errorsT1
4gcp_metrics — Cloud SQL metricsT1
5deploy_correlation — schema changes / migrationsT1
…known_issues · sentry · cloud_run · teams · computeT1
What a tree stores

An ordered list of (agent → action) steps, each tagged Tier-1/Tier-2 with a hit-rate — how often that step actually found the root cause.

How it learns

Designed to learn — loop not yet built. Each step carries a hit-rate, version, and skip-rule field, and every resolved incident is already persisted. Feeding that history back to re-rank steps and bump the tree version is the next phase; today the trees run at their v1 seeded order.

Why it matters

The agent will get faster and cheaper over time for each category — once the learning loop is built, without anyone rewriting prompts.
